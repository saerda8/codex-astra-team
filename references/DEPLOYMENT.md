# Codex Astra / Sol 多模型策略部署方案

版本：1.4.5 ｜ 生成日期：2026-09-08 ｜ 默认范围：全局所有项目

部署时同时同步 GLOBAL_DEPLOYMENT.md 中的节省额度规则：小任务直接做，大任务优先一个助手完成实现和测试，精简交接、减少重复读取和轮询，主会话只做必要审查与一次验收。协作数量不是验收目标，不修改用户选择的模型和档位，不引入硬拦截。

## 1. 目标与边界

目标是让最强模型处理最重要的问题，让次级强模型独立完成方案内的高级工作，让较小模型以满推理完成明确任务；在相同验收标准下评估用量、时间和返工。不能承诺三倍收益或固定节省比例。

GPT worker 是执行本文件的代理名称，本文件不假定它就是某个特定客户端。真正部署目标是用户要使用的 Codex 项目环境。若部署代理只有托管聊天容器，不能访问目标机器或目标仓库的生效配置，则在容器生成文件不等于部署到用户本机。此时交付待安装文件、具体阻塞项和未验证项，不假装已经改变本机模型路由。[S1]

默认修改用户级 Codex 配置、用户级六个角色和全局 AGENTS 规则，使所有项目的新任务自动继承；项目隔离部署仅在用户明确要求时使用。不新建常驻 MCP 服务、不注册第三方账号、不引入外部 API 调度器。Skill 是部署与维护入口；仅安装 Skill 不代表策略已经启用。全局具体流程以 `GLOBAL_DEPLOYMENT.md` 为准，本文件其余项目级路径用于可选的隔离部署。

全局运行触发条件固定为：主会话使用 `gpt-6-astra` 且推理档位为 low、medium、high、xhigh、max 或 ultra。从 Astra Low 起进入协作路由，以便额度较低的 Plus、Teams 五小时制账号尽早把执行工作交给 Sol、Terra、Luna。普通解释、追问、确认或状态问题直接回答，不触发协作、不调用 `spawn_agent`，也不恢复旧任务；非 Astra 主会话不触发本策略。

未明确确认主会话是 `gpt-6-astra` 且档位符合条件时，禁止输出 `本次路由：Astra`，禁止按 Astra 规则强制派工；按当前真实模型及通用规则正常执行。

保持 Codex 默认表达方式；本技能不规定开头、中间过程、结论或其他回复的格式、标题、措辞、顺序及示例。实际派工时只额外用一句话说明交给谁、做什么；使用已核实的角色和档位，不猜测，不把计划写成已经执行，不要求在进度或结尾重复。


明确执行型任务应优先落到实际派工。核心任务仍由 Astra 负责决策和总控，并尽量把独立调查、实现、测试或复核之一交给匹配角色；协作建议不能阻断项目本身继续执行。



全局模式使用四类事件做只读记录和一次性提醒：用户提示登记回合，工具调用前检查是否为较长任务，子智能体启动后记录，结束事件始终放行。检查脚本不得返回工具拒绝或 Stop 阻断；钩子未信任或未加载时不得报告运行时记录已生效。

普通解释、追问、确认或状态问题（例如“环境存在异常就拿不到岗位详情吗？”“这两者有因果关系吗？”）只做回答，不进入协作、不派助手、不恢复旧任务。明确的修复、修改、实现、排查或测试请求才进入协作流程。`UserPromptSubmit` 默认静默，仅记录状态；`additionalContext` 不得注入命令，检查脚本不得输出硬拦截。

Astra 主会话不以 MCP 派工代替模型角色派发。执行顺序为 Astra → Sol/Terra/Luna → 按需调用 MCP；通用 MCP 门禁应豁免 Astra 主会话。

MCP 是条件性能力：已加载、健康且适合当前子任务的 MCP 必须调用，由 Sol/Terra/Luna 按职责使用；没有、不可用、失败或不适合时不阻断，由当前模型角色继续完成。不得新增强制 MCP 门禁，也不得因 MCP 缺失阻止角色派工、验收或正常收尾。

当前运行时已经验证 `spawn_agent` 暴露真实角色字段，派发必须使用已验证的 `agent_type` 选择固定角色；`task_name` 只作为标签。部署到其他系统时必须重新核实该字段，缺失时报告协作能力不足，不得用标签伪装角色派发。

保留原有供应商、登录方式、网络、MCP、插件、其他项目设置和组织限制。不得读取或输出令牌、密钥、登录凭证；不得切换计费方式、购买额度、关闭审批、扩大沙箱权限、绕过钩子信任、自动提交/推送/发布或重置用户未提交修改。

## 2. 模型分工与思考等级

以下是用户确定的项目策略。它不是“模型越小，满推理在所有任务上越省”的实验结论；后续按实际验收数据评估。

| 固定角色 | 模型标识 | 档位 | 职责与使用时机 |
|---|---|---|---|
| 主会话 | gpt-6-astra | 当前回合实际档位 | 核心主导：总体架构、关键机制、重大取舍、关键实现与重要验收 |
| astra_xhigh | gpt-6-astra | xhigh（极高） | 特别复杂的核心问题、全局方案重审、跨模块重大疑难 |
| sol_high | gpt-5.6-sol | high（高） | 次级负责人：方案内的模块设计、复杂实现、调试、整合和日常验收 |
| sol_xhigh | gpt-5.6-sol | xhigh（极高） | 架构已定但逻辑复杂、难定位或边界验证要求高的工作 |
| terra_max | gpt-5.6-terra | max（满档） | 边界明确、中等复杂度的实现和集成测试 |
| luna_max | gpt-5.6-luna | max（满档） | 小任务、局部修复、批量修改、补测试与文档 |
| luna_explorer_max | gpt-5.6-luna | max（满档） | 只读探索、定位入口、追踪调用关系、整理证据 |

Astra 和 Sol 都不默认 max。Sol 不允许 none、low、medium。Terra 和 Luna 必须 max，包括探索任务，不允许自行降为 xhigh 或 high。模型标识参考官方模型页，GPT-5.6 的 max 设置参考官方发布说明；具体模型/档位组合的账号授权及客户端接受程度必须另行测试。[S5–S8、S11]

档位术语：none 表示不启用显式推理，low 为低，medium 为中，high 为高，xhigh 为极高，max 为满档。本方案实际使用的组合以上表为准；部署报告必须另外列出当前客户端检测到的各模型可用档位，不将一份通用名称列表冒充每个模型都支持的全集。Astra 模型页列出 low / medium / high / xhigh / max，GPT-5.6 发布说明明确提到 Work 和 Codex 的 max 设置。[S5、S11]

**关键兼容性提醒：** 核对时，模型资料和发布说明包含 max，而 Codex 配置参考中的 model_reasoning_effort 枚举仍只展示到 xhigh。不能据此猜测本机行为。必须检查当前版本的模型目录、配置解析和实际请求；max 不可用就标记阻塞，保留旧的可运行配置，不静默降档。[S2、S4、S5、S11]

### Astra 与 Sol 的边界

决定“系统怎样工作、必须守住什么核心规则”的任务，直接给 Astra；不要求 Sol 先失败。按已确定的总体规则把复杂工作完成，则优先 Sol。

Astra 负责租户隔离、权限边界、交易一致性、核心算法、任务调度机制等核心约束，以及公共契约、数据语义或整体架构的重大变更。代码少不代表低风险。Sol 可以独立设计模块内部实现、编写复杂代码、处理常规疑难、整合执行结果并完成普通验收，不必事事请示 Astra。

新增普通导出功能可以由 Sol 完成闭环；明确的参数校验测试可以直接交 Luna max；租户隔离漏洞即使只改两行，也应由 Astra 判断核心风险。重大任务通常是 Astra 定方案→Sol 细化/集成→Terra/Luna 执行→Sol 工程验证→Astra 关键验收；这不是要求每个任务都经过四层。

## 3. 硬配置与行为规则的区别

| 层级 | 实现位置 | 能做什么 | 不能夸大的地方 |
|---|---|---|---|
| 参数配置 | .codex/config.toml 与 .codex/agents/*.toml | 固定主模型、角色模型、推理强度、并发、子代理工具开关 | 写入文件不等于被当前会话加载 |
| 派发检查 | PreToolUse + model_guard.py | 对创建代理调用记录角色、参数和文件完整性结果 | 只审计和提醒，不能拒绝工具或阻止项目继续 |
| 语义分工 | 实际生效的 AGENTS 指令文件 | 指导核心/次级/执行任务分配、范围和验收 | 不能把文字规则当作操作系统权限或费用硬上限 |
| 生效证据 | 新会话、实际工具事件、线程元数据、测试记录 | 区分配置已写入与真实路由有效 | 模型自报身份不算证据 |

官方子代理文档说明，独立角色文件明确设置的 model 和 model_reasoning_effort 优先于派发对应参数；默认子代理参数只是兜底，不能代替角色文件。[S1]

钩子只做审计和一次性提醒，不替代沙箱或审批，也不参与工具放行。正常情况输出空 JSON；较长任务未按协作建议处理时可返回不阻断的 `systemMessage`。脚本不得返回工具拒绝或 Stop 阻断。[S3]

## 5. 部署前检查

确认操作系统、Shell、真实项目根目录、Codex 形态和版本、CODEX_HOME、Python 解释器。原生 Windows 与 WSL 分别处理；脚本要求 Python 3.11+，缺少时明确报告，不自动安装系统组件。

先查看本机 --help 再使用具体命令。可用时检查 codex --version 和 codex login status；不执行重新登录，不读取 auth.json。检查用户级和项目级配置、启动参数、所选 profile、上级/子目录指令以及组织限制。项目层是否受信任、是否被高优先级设置覆盖，均要记录。[S2、S9]

读取目标客户端的完整 model/list，遍历 nextCursor，把所有分页合并为 data 数组且 nextCursor 为 null 的 JSON，或保存同结构 result 对象。目录只能来自当前目标客户端，不用合成样例冒充。用脚本执行：

```text
python scripts/strategy.py catalog-check --catalog <完整模型目录JSON>
```

核对本包需要的模型/档位组合。目录校验不发起模型调用，也不证明授权或路由已经成功；后面要做真实小型测试。[S4]

检查当前版本支持独立角色文件、agents.enabled、并发字段、多代理和钩子字段。若需要旧版专用适配，先生成待启用说明；不把未经测试的替代格式直接装入活动配置。默认包面向已核对的当前独立代理格式，不自动维护两套同名注册。

检查同名角色及已有策略/钩子的冲突。保留其他角色文件，但本策略的派发白名单默认只接受六个登记角色；若用户原先依赖其他角色，明确报告这项行为变化。不得为了避免冲突擅自扩大白名单或改变用户模型规则。

## 6. 候选文件、备份与合并

### 6.1 先在非自动加载目录生成候选

从技能根目录运行离线测试，然后生成新的候选目录：

```text
python scripts/test_strategy.py
python scripts/strategy.py stage --project <项目绝对路径> --out <新的候选目录>
```

stage 只生成候选文件，不覆盖活动配置。它会提供主配置片段、六个角色、项目规则、派发审计脚本、钩子片段，以及当前 Codex 与旧式客户端两种未验证的参数适配器样例。

主配置目标：

```toml
model = "gpt-6-astra"
model_reasoning_effort = "high"

[features]
multi_agent = true
hooks = true

[agents]
enabled = true
max_concurrent_threads_per_session = 2
default_subagent_model = "gpt-5.6-luna"
default_subagent_reasoning_effort = "max"
```

每个子代理配置都显式写 model、model_reasoning_effort 和 [agents] enabled=false；探索角色另写 sandbox_mode="read-only"。不要因为 TOML 语法能解析，就认为所有字段已被该版本接受。[S1、S2]

### 6.2 备份

在修改目标文件前运行：

```text
python scripts/strategy.py backup --project <项目绝对路径> --backup <新的备份目录>
```

备份只覆盖本方案登记的目标文件，不复制整个用户配置目录或凭证。保存每个文件原先是否存在、校验值和权限。目标文件或其父目录是符号链接时，脚本会拒绝自动修改；部署代理应报告并提供可审查的手动合并计划，不绕过检查。

### 6.3 增量合并

把 config.fragment.toml 合并到现有 .codex/config.toml 的正确位置，不重复创建表、不把根级键误放到某个表内。不用简单的全文追加处理已有 TOML。保留不相关配置和注释；修改旧别名导致双重并发设置时核对优先级并消除冲突。

将六个角色写入对应文件；同名旧文件先备份再审查差异。将 model_guard.py 放入 .codex/hooks/。把钩子片段按事件数组合并到现有 hooks.json，保留其他处理器并避免重复登记。若项目已有内联 [hooks]，不要重复注册同一个审计脚本；采用经核验的一种表示，并同步调整本包的静态校验后重新测试。[S3]

将 PROJECT_RULES.md 的标记区间合并到实际生效的指令文件；重复部署只替换该区间，不覆盖用户其他规则。已有 AGENTS.override.md 时优先检查它；上级和更深目录规则也可能影响目标任务。[S9]

增量加入忽略项 `/.codex-strategy-local/`。model-policy.json 包含机器路径与本地基线，也建议忽略 `/.codex/model-policy.json`，不要自动提交；其他策略文件是否共享到仓库由用户决定。

生成 docs/CODEX_ASTRA_WORKFLOW.md：包含模型矩阵、日常用法、停止条件、使用范围、检查与回滚入口。不要把整份部署文档长期灌入每个任务的 AGENTS 上下文。

## 7. 派发检查脚本与完整性基线

脚本检查角色白名单、冲突参数、目标目录和完整性基线。异常只记录审计，不返回工具拒绝。审计不记录任务正文或凭证。

**先核实真实工具参数，再接通脚本。** stage 产生 `adapter.current-codex.example.json`（角色字段为 `task_name`）和 `adapter.agent-type.example.json`（角色字段为 `agent_type`），通用 `adapter.example.json` 指向当前 Codex 形态。三者默认均为 `verified=false`。部署代理必须从当前客户端工具 schema 或受控真实事件确认工具名、角色字段、模型/档位覆盖字段和允许输入字段，并保存不含敏感数据的 `tool-schema-evidence.md`。未经核验不得把 false 改成 true。

将已核实的配置保存为 `adapter.json`，`evidence_ref` 使用目标项目内的相对文件路径。`role_fields` 只登记当前工具真实提供的角色字段；`allowed_input_fields` 只登记真实输入字段。审计脚本同时兼容旧版单值 `role_field`，但新部署使用 `role_fields`。若工具没有可验证的角色字段，保留 `verified=false`，只安装角色配置、语义规则和非阻断审计，不得宣称能够强制派工。

```text
python scripts/strategy.py seal --project <项目绝对路径> --adapter <已核验适配器JSON>
python scripts/strategy.py verify --project <项目绝对路径>
```

seal 建立基线，不是数字签名或不可篡改存储。能修改守卫和策略文件的同一权限主体仍可改变规则；这是防误配置工具，不是对抗同权限恶意进程的安全隔离。不能声称它形成绝对成本上限。

通过正常客户端流程审核并信任项目及钩子。禁止使用跳过钩子信任的参数或直接修改信任库。主配置变更、角色配置变更、钩子变更和新项目规则分别核实是否需要新会话或重启。[S3、S9]

## 8. 真实验证与验收

分开保存四种证据：离线测试、静态文件校验、有效配置读取、真实运行结果。使用 config/read 或当前版本等效能力读取合并配置；不能用临时 --model 覆盖后测试成功，反过来声称磁盘主模型已经生效。[S4]

| 测试 | 应看到的结果 |
|---|---|
| 主会话 | 显示当前回合实际模型与档位，并有线程/请求元数据证据 |
| 六个角色 | 各角色实际采用对应模型和档位；不能只询问模型自己是谁 |
| 真实合法派发 | 能进入固定角色并完成一个极小的无业务副作用任务 |
| 未登记角色 | 审计记录异常角色，但不阻止客户端按自身规则处理 |
| 降档或模型覆盖 | 审计记录冲突参数但不拒绝工具；若无此参数则注明不适用 |
| 配置漂移 | 在候选副本完成离线检查，再验证审计脚本确实读到有效基线；恢复后重验 |
| 禁止递归 | 子角色按配置不继续派生；审计脚本不承担强制阻断 |
| 并发上限 | 核实两个子代理上限；受控尝试超限时应由客户端限制，不修改配置提升上限 |
| 只读探索 | 实际权限符合预期，不能只看 sandbox_mode 文本 |
| 原有审批 | 审计脚本不会额外授予或拒绝权限；原有审批和沙箱仍有效 |

用最多两个并发线程，每个模型/档位组合一个极小任务做验证，不执行大型基准和无穷重试。真实测试会消耗目标账号正常额度；不另开收费通道。

样例任务在 .codex-strategy-local/smoke/ 内完成：Luna 写一个小型纯函数与测试；Terra 处理一个明确的边界条件；Sol 分别验证常规和复杂逻辑；Astra 极高处理一个很小的核心约束判断。可分批串行复用样例，不让两个代理同时修改同一文件。核对实际调用元数据；验证完成即关闭不用的代理。

若无法获得模型或档位元数据，只能报告“配置已设置，但实际模型/档位路由未验证”。钩子未信任、脚本无法启动或当前环境不暴露这些控制时，明确“审计记录未验证生效”，不能靠离线构造 JSON 的测试结果替代。

主代理语义分工仍是行为规则。记录几个代表任务实际分配给谁，检查 Astra 是否仍包办执行；不得声称 PreToolUse 已强制所有任务正确分层。

状态只选：

- **已验证生效**：配置加载、账号调用、模型与档位证据、审计记录、非阻断提醒和样例验证均通过。
- **已配置，待验证**：文件已合并，但缺少信任、重启、权限或运行证据。
- **部署受阻／仅生成候选**：缺少必要模型、max、客户端能力或目标环境权限。

坏配置影响现有启动时应恢复本次变更，不留失效配置作为默认。不能为了宣布成功而降档、换模型或切换账号/计费方式。

## 9. 使用流程与任务交接

日常任务不再重新部署。项目规则已被验证自动加载后，用户直接描述目标即可。主会话只进行必要的分类和核心决策，非核心完整任务由 Sol 收口，不重复研究整仓或重复审查每个小改动。

统一交接格式：

```text
任务编号：
目标与必要上下文：
允许读取范围：
允许修改范围：
禁止事项与核心约束：
依赖关系：
验收命令与完成标准：
停止并上交的条件：
交付：改动摘要、实际测试结果、风险和待决问题。
```

任何执行代理最多首次尝试加一次针对性修正；返回的是可定位的证据，不是大段无关日志。评估单位是“一个通过验收的任务”，不是生成代码行数、线程数或单独的模型单价。记录实测用量，不可得就填 null；不把 API 单价当订阅额度精确消耗。[S1]

## 10. 备份、回滚与维护

文件合并和验证结束后，对同一个备份运行：

```text
python scripts/strategy.py finalize-backup --project <项目绝对路径> --backup <该次备份目录>
```

只有部署代理仍掌握本次变更且没有并发用户编辑时才记录后置基线。它描述部署结束状态，不得在用户后续修改后重新记录来抹掉差异。

回滚：

```text
python scripts/strategy.py rollback --project <项目绝对路径> --backup <已记录后置基线的备份目录>
```

脚本在写入前先验证所有需要恢复的文件和备份字节。发现部署后的改动则在任何恢复写入前停止，交付差异供人工合并。原有文件恢复备份，新增文件仅在仍是部署版本时删除；不使用 git reset --hard，不删除业务文件，不自动移除用户后续内容。

若部署在记录后置基线前异常中断，不能盲目 finalize 再回滚；结合备份、候选和本次工具日志确认哪些内容属于本次修改，再做精确恢复。并发改动不明确时停止自动恢复。

模型、客户端、项目路径或策略配置升级后重新核验适配器与实际路由。策略文件的合法变更也会触发漂移；经用户授权维护后重新生成基线，不自动原地绕过拒绝。
