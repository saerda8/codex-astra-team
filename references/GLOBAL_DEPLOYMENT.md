# 全局部署

默认安装到用户级 Codex 配置，使所有项目的新任务自动继承，不要求每个项目复制 Skill 或再次部署。

## 写入范围

- 增量合并 `assets/config.global.fragment.toml` 到用户级 `config.toml`。
- 将十二个角色文件复制到用户级 `agents/`。
- 将 `scripts/astra_turn_guard.py` 安装到用户级 `hooks/`，并把 `assets/hooks.global.fragment.json` 的四类事件增量合并到用户级 `hooks.json`；将 `<CODEX_HOME>` 替换为真实目录，保留现有钩子。
- 将 `assets/PROJECT_RULES.md` 的标记区间增量合并到用户级 `AGENTS.md`。
- 将完整 Skill 复制到用户级 `skills/codex-astra-team/`，供以后检查、升级和回滚指导使用。

修改前分别备份这些文件。保留供应商、账号、网络、MCP、插件、上下文窗口、审批和沙箱设置。新任务或重启客户端后才会加载新的模型与角色配置。

合并后通过 `/hooks` 审查并信任新定义。Codex 按钩子内容哈希记录信任；未信任时会跳过，不能报告检查脚本已加载。

## 当前 Codex 与其他系统

当前运行时已经验证 `spawn_agent` 暴露真实角色字段。派发时必须使用已验证的 `agent_type` 选择固定角色；`task_name` 只是任务标签，不能冒充角色选择。

其他客户端仍须重新核实自己的工具结构。若真实暴露 `agent_type` 或其他明确角色字段，可选择对应适配器并记录证据；若没有可验证角色字段，保持适配器 `verified=false`，只安装不阻断的审计记录，并明确报告“协作未启动”，不得用任务标签假装已派工。

## 自动使用

额度优化只减少重复派工和上下文开销，不豁免 GPT-6 Astra 或 Sol 在 Medium 及以上的明确执行任务。
- 普通问答、追问、确认和状态交流直接回答。GPT-6 Astra 或 Sol 的 Low 执行任务可由主模型直接完成；Medium 及以上的明确执行任务不论大小都要真实派工。
- 大任务优先交给一个匹配角色完成完整的实现和相关测试；已有助手适合时复用。新助手只传必要目标、证据、允许范围和验收标准，独立任务不继承整段历史。只有确有独立并行工作才增加第二个助手。
- 主模型不重复助手正在做的调查；结果到达后只审查必要差异并完成一次与风险相称的验收。已有有效测试证据可复用，有新修改、失败或疑点才重跑。
- 已读且未变化的技能与文档不重复加载；独立读取合并一次，日志先筛选、汇总再输出，禁止把完整历史、工具目录或巨型日志塞回上下文。
- 等待优先使用完成通知或阻塞式等待；无新证据不反复查询，不为汇报状态启动其他任务。进度说明只报新发现。
- MCP 同样计入启动和协调成本；GPT-6 Astra 或 Sol 在 Medium 及以上先真实派给一个匹配角色，有合适且可用的 MCP 时再用于独立执行部分，不为凑调用增加一层派工。上述优化不改变用户选择的模型/档位、权限或非阻断原则。

触发条件只有一个：当前主会话使用 `gpt-6-astra` 或 `gpt-6-sol`，且推理档位为 medium、high、xhigh、max 或 ultra。从 Medium 起进入协作路由；Low 仍可直接完成。普通解释、追问、确认或状态问题直接回答，不触发协作、不调用 `spawn_agent`，也不恢复旧任务；其他主会话不触发本策略。

未明确确认主会话是 `gpt-6-astra` 或 `gpt-6-sol` 且档位符合条件时，禁止声称触发 GPT-6 协作路由，禁止强制派工；按当前真实模型及通用规则正常执行。

保持 Codex 默认表达方式；本技能不规定开头、中间过程、结论或其他回复的格式、标题、措辞、顺序及示例。实际派工时只额外用一句话说明交给谁、做什么；使用已核实的角色和档位，不猜测，不把计划写成已经执行，不要求在进度或结尾重复。


GPT-6 Astra 或 Sol 在 Medium 及以上的明确执行型任务必须先真正派工。Astra 按复杂度把高级工程执行交给 sol6_high、sol6_xhigh 或 sol6_max。GPT-6 Sol 主会话不得派给 sol6_ 角色来满足派工，应使用 Luna、Terra 或旧 Sol。GPT-6 Luna 按 High、XHigh、Max 分档；Terra 继续作为平衡型备选。



检查脚本记录已关联到父回合的 `SubagentStart`、成功返回任务名的 `spawn_agent` 或已有角色成功互动的 `followup_task`，但这些记录不作为工具放行条件。所有本地工作、派工、查看、等待和正常收尾始终放行；工具启动失败时允许明确报告阻碍并结束。

普通解释、追问、确认或状态问题（例如“环境存在异常就拿不到岗位详情吗？”“这两者有因果关系吗？”）只做回答，不进入协作、不派助手、不恢复旧任务。明确的修复、修改、实现、排查或测试请求才进入协作流程。`UserPromptSubmit` 默认静默，仅记录状态；`additionalContext` 不得注入命令，检查脚本不得输出硬拦截。

GPT-6 Astra 或 Sol 主会话不以 MCP 派工代替模型角色派发。先启动 Sol/Terra/Luna，再由该角色按需要调用 MCP Worker；通用 MCP 门禁必须豁免 GPT-6 主会话，不能和回合检查并列要求两次前置派工。

MCP 是条件性能力：已加载、健康且适合当前子任务的 MCP 必须调用，由 Sol/Terra/Luna 按职责使用；没有、不可用、失败或不适合时不阻断，由当前模型角色继续完成。不得新增强制 MCP 门禁，也不得因 MCP 缺失阻止角色派工、验收或正常收尾。

## 共享到其他系统

其他系统收到 ZIP 或独立 Markdown 后，先核实它的模型标识、推理档位、自定义角色格式和派发字段。支持用户级配置时采用本页；只支持项目配置时再使用 `references/DEPLOYMENT.md`。所有系统都只使用全局角色、语义规则和非阻断审计，不能引入强制拦截能力。
